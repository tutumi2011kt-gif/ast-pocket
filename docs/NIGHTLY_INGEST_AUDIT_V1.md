## このPRで追加するもの

05:25 JST（UTC 20:25）に GitHub Actions `AST Pocket Nightly Ingest Audit` を起動。対象は当日の03:00 JST以降に作成予定の content/weekly/YYYY-MM-DD.md。

1. mainのcontent/index.jsonと実ファイルが一致すれば `published`。
2. mainに登録がなくても、該当日のWeeklyを含むオープンPRがあれば `pending_review`。PR番号を出す。
3. どちらも見つからなければ `unconfirmed`。**『学習0件』とは判断しない**。Actionsを失敗状態にして原因調査を促す。
4. indexにだけファイルがある、あるいは実ファイルだけがある不整合は `unconfirmed`。
5. 04:00より前の手動実行では `not_due`（対象日の03:00実行中の可能性）。

監査はGithubの公開成果物と公開PRの**存在だけ**を見るため、ChatGPTの会話内容、患者情報、アクセス制約、臨床情報の真偽は確認できない。PRの中身も検証せず、日付のWeeklyファイルが含まれるかだけを判定する。

Actionsのサマリーに結果・対象日・PR番号と理由を記載する。データを作成したり、自動マージしたりしない。無断で臨床Knowledgeや問題集を変更しない。

## 本当の取り込みが成功したかの確認方法

- 第1関門：03:00のChatGPTタスクが実行されたか（日時）。
- 第2関門：アクセス可能だった学習会話と取得エラー・0件を分けた実行報告があるか。
- 第3関門：患者情報・院内情報・秘密を除去した、出典候補のある学習要約が得られたか。
- 第4関門：Githubブランチ・PRにその日のWeeklyとindex変更が**実際に存在**するか。
- 第5関門：GitHub Actions Validateが成功し、内容確認の後にmainへマージされたか。
- 第6関門：Pages deploy成功後、AST Pocketの該当8章へdraft学習候補が表示されたか。

監査単独で証明できるのは第4〜5関門の一部だけ。第2〜3関門はタスクの実行報告とアクセス・保存権限を追加で確認しなければならない。

## 起こりうる状況と扱い

| 観測 | 運用 |
| --- | --- |
| published | 既存Weeklyに登録。自動取得が網羅的・医学的にverifiedという意味ではない |
| pending_review | PRはできたが公開待ち。レビュー後にマージ |
| unconfirmed | 保存を確認できない。学習0件、取得失敗、GitHub権限不足、個人情報保護による停止等を切り分ける |
| not_due | まだ03:00処理後の監査時刻ではない |
| 取得した学習が本当に0件 | 03:00タスク側が、アクセスした範囲・期間・0件を明記。GitHub側ではゼロを推測しない |

監査は毎日、学習が全くなかった正常な日でも`unconfirmed`とすることがある。**誤解を避けるための意図的な厳格さ**であり、取り込みが実際に失敗したと断定するものではない。

## 残る技術課題

- ChatGPTのタスクからGitHubへ安全に書き込む実行経路の安定化。GitHub Actions単体では個人ChatGPT会話を読めず、現行repoに自動取り込みAPIは存在しない。
- 03:00タスクの詳細な実行結果とGitHub PR/commitの突合（権限・実行環境・コンテキスト依存）。
- 学習0件・アクセス失敗・安全保留を区別した機械的な記録（患者情報を含まない専用ステータスのみを検討）。
- アラートが必要な場合、GitHub Actionsの失敗通知やChatGPT側の通知設定を別途確認。
- 出典照合や医学的な意味分類は引き続き承認フローが必要。
